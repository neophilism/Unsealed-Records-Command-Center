# URC-02 backend-for-frontend trust boundary

The BFF validates RS256 signatures against a server-configured JWK set, exact issuer and audience, a five-minute token lifetime, and a signed per-label grant. It does not accept browser-supplied identity flags or labels. Requests without a matching active grant never reach the engine. Only server-configured report routes are outbound. Redirects and unexpected response labels fail closed. Engine credentials stay in the server process. Large decimal values must be strings in the upstream JSON contract.

Run with Node 20 or newer and `node --test tests/bff-*.test.mjs`. Start with `node src/bff/main.mjs`. Configure BFF_ISSUER, BFF_AUDIENCE, BFF_JWKS_JSON, ENGINE_ORIGIN, ENGINE_TOKEN, BFF_REPORT_ROUTES_JSON, OIDC_AUTHORIZATION_ENDPOINT, OIDC_TOKEN_ENDPOINT, OIDC_REDIRECT_URI, OIDC_CLIENT_ID and BFF_SESSION_KEY_BASE64 on the server. The session key must decode to exactly 32 random bytes. The JWKS must come from the trusted identity issuer and rotate with deployment. Example route configuration: `{"streams":"/v1/labels/{labelId}/reports/streams"}`. Do not enable a route until the upstream Music Operations Engine contract and tenant enforcement are verified. Health is at `/healthz`.

The interactive login uses an OIDC authorization-code exchange with PKCE, state and nonce checks. Sessions are encrypted in `__Host-` HttpOnly/Secure/SameSite cookies and expire with the five-minute ID token. The configured issuer must include signed label grants in its ID token; no browser-supplied claims are trusted. There is no local first-admin bootstrap.

Every report additionally checks current membership before the engine request and again before releasing its response. The default is denial. Production startup requires `BFF_MEMBERSHIP_FILE`, an absolute path to a private regular file (mode 0600) with the following schema. Manage the parent directory through trusted deployment administration. Replace the complete file atomically; never modify it through an unauthenticated or browser-facing endpoint. Do not commit live membership records. Missing, malformed, stale, duplicate, wrong-issuer or symbolic-link files deny access.

```json
{"version":1,"revision":1,"issuer":"https://trusted-issuer.example","issuedAtMs":1800000000000,"validUntilMs":1800000600000,"grants":[{"subject":"issuer_subject","labelId":"label_0001","role":"viewer","active":true,"notBeforeMs":1800000000000,"expiresAtMs":1800000300000}]}
```

The timestamps above are illustrative expired fixtures, not deployable grants. The validity window must be no longer than 24 hours. Refresh it through the trusted control plane before expiry. Bind the subject to the configured issuer's immutable subject identifier. First-admin provisioning is an explicit deployment action: grant only a verified issuer subject and explicitly authorized labels; email addresses and first-login order never confer ownership. Effective access is the intersection of the signed token and current file, with the lower role and earliest expiry. Set `active:false` or remove the grant to revoke it. Each replica must receive the updated file before revocation can be considered global; deployments needing a central membership service must supply an authoritative `checkMembership` adapter instead. No cross-replica consistency is claimed for independent files.

Token and report JSON bodies are consumed with byte limits, strict UTF-8 and cancellation on overflow or timeout. The token limit is 20 KB and report limit is 1 MB; content-length cannot bypass streaming limits. Reports preserve source provenance and decimal strings without relabeling cached or synthetic data. Failed requests expose only a fixed public error and can be retried explicitly; there is no automatic financial/provider operation retry.

Remaining work includes real issuer/account provisioning, verified upstream domain contracts and source ordering, frontend integration, CI coverage, and deployment smoke tests. The existing GitHub workflows do not run BFF product tests. Local HTTP tests use generated fixture keys and simulated providers; they do not establish live identity or Engine interoperability.
